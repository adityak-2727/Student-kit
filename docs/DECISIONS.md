## Changes during implementation

### 14 October 2026 — verified foundation baseline

- D03: Node 24 LTS is the runtime line; this machine runs 24.13.0. `engines` permits compatible 24.x patches and `.node-version` records the tested runtime. Prefer the latest security-patched 24.x when provisioning. pnpm 12.11.2 is pinned in `packageManager`, with exact direct dependency versions and `pnpm-lock.yaml`.
- Selected Next.js 16.4.0 and React/React DOM 19.3.0 from stable registry tags and official documentation. Next requires Node >=20.9; the future MongoDB 7 components require >=20.19; Node 24 meets both. TypeScript 5.9.3 is a conservative supported stable baseline (not the newer 7.0 compiler), with strict, unchecked-index and exact-optional checks. Compatibility is additionally exercised by the actual typecheck/build.
- D10: Use stable `next-auth` 4.24.15 and its v4 API when implementing Google identity, rather than v5's beta install path. Registry peers explicitly include Next 16 and React 19. Preserve JWT session minimization, Google issuer/subject mapping, encrypted profile payloads, no generic plaintext adapter, and supported protocol protections. Application `AUTH_*` settings will map explicitly to v4 options; configure `NEXTAUTH_URL` from validated `APP_ORIGIN`. No auth dependency is installed yet.
- Date library: Luxon 3.7.2 uses Node's IANA/Intl timezone support. Day boundaries add calendar days rather than 24-hour durations. Local midnight and 23/25-hour DST day tests form the first evidence. Manual ambiguous/nonexistent scheduling input and recurrence policy remain for the scheduling implementation; these helpers do not guess wall-time offsets.
- D16: Reserve MongoDB 7.7.0 with `mongodb-client-encryption` 7.2.1 (official 7.x component compatibility). They are not needed for the scaffold and are not installed. Native loading, real CSFLE, tampering, container packaging, KMS and backup recovery remain unverified risks to prove before data persistence. Target a Node 24 Debian/glibc container; no host, paid resource, or public deployment selected.
- Runtime mode reconciliation: the original env template's `APP_MODE=live` would imply services that do not exist. Replace it with explicit `foundation` for this build, reject live/demo and any authentication bypass, and leave integration placeholders unused by the public scaffold. Later live-mode introduction requires the security gates in `SECURITY.md`; there is no silent fallback. Production integration preflight rejects local encryption keys. Foundation startup validates only the settings used by this credential-free public surface.
- The product, XP, streak, privacy, and data-model contracts have no conflicting rule requiring a change. Full design tokens/primitives and Manrope/Newsreader self-hosting remain for the visual-system work; this entry point uses local system fonts without remote requests.

Radix, Motion, Recharts, React Hook Form, and native database/auth dependencies are deferred until used. Lockfile peer resolution plus actual checks verify the installed subset; registry compatibility alone is not live-integration evidence.

Installer follow-up: pnpm 12 requires non-auth settings in `pnpm-workspace.yaml`, so exact-version, strict engine/peer checks and one reviewed native build (`unrs-resolver@1.12.2`, used by the linter) are configured there. No blanket build-script permission is enabled. ESLint 9.39.5 is the newest 9.x patch; Next's installed React and JSX accessibility plugins still declare only ESLint <=9, so adopting 10.12.0 would violate their peer contracts. Recheck that boundary with a future Next tooling update.

Startup verification: Next instrumentation aborts request preparation for invalid configuration but Next can still bind a port before that error. Dev/build/start therefore run the configuration CLI first, which terminates with exit 1 before launching Next for invalid settings. The instrumentation hook remains a secondary runtime defense.

## Decisions requiring real environment information

### 14 October 2026 — Google and encrypted account foundation

- Installed stable NextAuth **4.24.15** (declared Next 16/React 19 peers). v5 remains `5.0.0-beta.32` and is not selected. Use only v4 [App Router initialization](https://next-auth.js.org/configuration/initialization), [Google provider](https://next-auth.js.org/providers/google), [callbacks](https://next-auth.js.org/configuration/callbacks) and [REST protocol](https://next-auth.js.org/getting-started/rest-api). No generic plaintext database adapter, email linkage or retained Google API tokens. Google ID-token verification/state/PKCE/nonce stay in the library. JWT output contains internal ID/version/authentication time only; library adds expiry/issue/jti metadata. Sessions expire after seven days from authentication even if JWT transport is refreshed; protected repository access rechecks account status/version.
- Installed MongoDB **7.7.0**, official mongodb-client-encryption **7.2.1** and AWS credential-providers **3.1148.0**. Driver/native 7.x require Node >=20.19 and fit Node 24.13; [official v7 compatibility notes](https://raw.githubusercontent.com/mongodb/node-mongodb-native/main/etc/notes/CHANGES_7.0.0.md) and [explicit encryption contract](https://www.mongodb.com/docs/manual/core/csfle/fundamentals/manual-encryption/). Allow only the exact native package's installation script. Chose settled AWS SDK release instead of newly published 3.1151.0; removed its unused pnpm release exception. libmongocrypt 1.20.1 loads and performs encryption on Windows x64; Linux/container and AWS mode still need actual evidence.
- Per-user DEKs use unique key aliases and official randomized `AEAD_AES_256_CBC_HMAC_SHA_512-Random`. Whole validated identity envelopes include schema/owner/document/kind; no plaintext profile duplicate. Queryable metadata follows SECURITY.md. Mongo validates binary payloads; repository additionally requires BSON subtype 6 (Mongo `$jsonSchema` binData alone cannot constrain subtype). HMAC version/key must remain stable until a dual-read migration is implemented; no silent direct rotation.
- First login reserves a unique HMAC identity, provisions a wrapped key and disabled built-in domain metadata, then activates only with ciphertext. Interrupted reservations retry safely; onboarding remains pending and chooses domain enablement in Phase 4. Concurrent tests prove one user/key and four domains. Username/timezone/alias/avatar and rewards remain later scope.
- Migrations run explicitly with separate privileges, record actual-definition checksums, and reject mismatches. Serving requests verify the installed schema/index contract; they do not create indexes. Production startup proves key wrapping/decryption with a temporary key before serving; failures remain closed. Application records are not written by that probe. Wrapped probe cleanup interruptions require maintenance, not deletion of user keys.
- Canonical fixed origins and callback destinations; query overrides of OAuth scopes/redirect URI rejected. Library CSRF protects protocol actions; strict Origin/content-type plus capped streams protect app/auth POSTs. Signed per-browser limiter identities use the library's JWE API with a distinct salt; Mongo windows enforce 10/minute per browser and a separately configurable 300/minute deployment safety ceiling. Cookie renewal/automation means ingress IP/bot controls are also required. No arbitrary forwarding headers are treated as trusted identity.
- Follow [Next's nonce CSP guidance](https://nextjs.org/docs/app/guides/content-security-policy): fresh script nonces and strict-dynamic, no inline/eval scripts in production, no objects/frames, local fonts, no-referrer, private/no-store. Inline styles remain allowed because Radix positioning and the existing responsive editor use inline styles; this is an explicit style-only exception. HTTPS gets HSTS; TLS termination and ingress restrictions are host requirements.
- The installed React auth helper redirects even after some non-success JSON responses. The small client uses the official CSRF/POST REST protocol and validates HTTP success/allowed destinations before navigation; simulated failures are tested, and no OAuth or JWT cryptography is handwritten. No valid test identity can be enabled in production.
- Real Google, Atlas, KMS permissions/TLS, native container and recovery are not proven by local tests. The user confirmed no external setup yet; exact private steps are in SETUP-AND-DEPLOY.md. No resource or public host was created.
- Node CLI modules use erasable TypeScript class fields; `erasableSyntaxOnly` prevents unsupported parameter properties under Node's stable type stripping. Migration/encryption CLIs were actually invoked and fail safely on missing setup. Local key preparation writes no values to output, preserves existing keys and remains Git-ignored; this workspace's Windows ACL was restricted and verified for the current user/SYSTEM/Administrators.
